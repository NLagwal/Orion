# Orion - Adaptive Endurance Coaching Model

Orion is a Qwen 2.5 3B model fine-tuned to turn daily training telemetry into a
structured coaching decision. The labels are synthetic, built from real wearable
data, and evaluated on 235 held-out examples.

This repo is the model/data/eval side only. The web UI is not here.

## Results

| Variant | Action accuracy | Escalation recall | JSON valid | Schema valid |
|---|---:|---:|---:|---:|
| LLM only | 68.5% | 81.8% | 100% | 99.1% |
| GBM router | 88.5% | 86.4% | - | - |
| Hybrid | 88.5% | 86.4% | 100% | 100% |

The router is where the accuracy comes from. Guardrails did not fire on this
split, so the hybrid matches the router. They exist for safety cases (injury,
ACWR >= 1.50, elevated RHR + fatigue), not to raise accuracy.

The LLM was given the router's action and followed it in all 235 cases. Its
independent accuracy is the 68.5% LLM-only number. Three escalations were still
missed, so 88.5% is not a safety guarantee.

## What it does

Input: resting HR and trend, sleep, ACWR/training load, subjective check-in,
injury flags, and athlete profile.

Output: JSON with an action (`MAINTAIN_PLAN`, `SWAP_TO_ZONE2`, `REST_DAY`,
`MODIFY_INTERVALS`, or `ESCALATE_TO_HUMAN`), a one-sentence rationale, a
modified workout, confidence, and escalation metadata.

## Model

- Base: `Qwen/Qwen2.5-3B-Instruct`
- Fine-tuning: QLoRA (4-bit) via Unsloth
- LoRA: rank 32, alpha 64, dropout 0, attention and MLP projections
- Training: 2 epochs, 280 optimizer steps
- Final train loss: 0.2745
- Validation cross-entropy: 0.3062
- Export: merged 16-bit checkpoint to Q8_0 GGUF (3.28 GB)

Full config and commands: [`docs/TRAINING.md`](docs/TRAINING.md).

## Data

- 2,230 training examples and 235 held-out evaluation examples
- Inputs sampled from PMData (16 athletes, about 5 months) and a 2025
  HRV/sleep-diary dataset
- Labels generated by a frontier model from an explicit rubric, then filtered
  through the deterministic guardrails
- 54% of train rows and 57% of eval rows have at least one missing critical
  telemetry field
- `MODIFY_INTERVALS` has only 5 held-out examples, so its per-class metrics are
  not reliable

## Latency

`llama-server`, Q8_0 GGUF, RTX 4070 Laptop, full 235-example hybrid run:

- p50: 2.79s
- p95: 3.10s
- throughput: 59.3 tok/s
- prompt processing p50: 78ms (50-prompt run)

Results: [`benchmarks/hybrid_results.json`](benchmarks/hybrid_results.json) and
[`benchmarks/latency_results.json`](benchmarks/latency_results.json).

## Reproduce

LLM evaluation:

```bash
python scripts/eval_merged.py \
  --model_dir coach_merged_16bit \
  --eval_file data/synthetic_coaching_eval.jsonl \
  --max_samples 0 \
  --output_file benchmarks/eval_results.json
```

Action router:

```bash
python scripts/train_action_router.py
```

Hybrid evaluation (start `llama-server` first):

```bash
python scripts/eval_hybrid.py \
  --server_url http://127.0.0.1:8080 \
  --max_samples 0 \
  --output_file benchmarks/hybrid_results.json
```

Latency:

```bash
llama-server -m coach.gguf --host 127.0.0.1 --port 8080 -ngl 99 -c 2048
python scripts/bench_latency.py --max_samples 50
```

## Limitations

- Labels are synthetic, not real coach decisions.
- 54% of training rows and 57% of eval rows have missing critical telemetry.
- The router runs as a local FastAPI sidecar; it is not wired into a production
  client.
- Three of 22 escalations were missed on the held-out split.
- This is a 3B edge model, not a clinical or production coaching system.
